# Repository agent contract — visual-first science and implementation

At the **start of every Antigravity, Hermes or other implementation-agent work session**, read [README.md](README.md), the [visual product vision](docs/PROPULSION_EXPLORER_VISION.md), [scientific charter](docs/SCIENCE_CHARTER.md), [Exodus model contract](docs/EXODUS_MODEL_CONTRACT.md), and [roadmap](docs/ROADMAP.md). This applies to UI, documentation and physics tasks alike. Verify live GitHub status before declaring progress.

## Owner's visual-first north star

**Deliver a beginner-friendly Propulsion Explorer, not merely a sequence of scientific code reviews.** A user should be able to rotate a 3D electrode arrangement, see electric fields and forces, understand what reacts against what, adjust meaningful inputs, and explore a provenance-aware *experimental* test-article specification. The product must answer **What am I seeing? Why does it happen? What changes it? How could we test it?**

Build a useful **V0 educational 3D scene in parallel with P2 scientific remediation**. It may show clearly marked schematic or provisional physics; it must not advertise net propulsion as measured or accepted. Keep the formal P0–P4 scientific gates and independent reviews unchanged. Distinguish conventional electrostatics, the cited Exodus H1 hypothesis, mathematical scalar waves and any proposed physical scalar-field theory. Refer to [the owner-facing vision](docs/PROPULSION_EXPLORER_VISION.md).

## Roles and tools

- Implementation agents (including Antigravity and Hermes) may perform scoped development using relevant [Superpowers](https://github.com/obra/superpowers), [Matt Pocock skills](https://github.com/mattpocock/skills) and [Scientific Agent Skills](https://github.com/k-dense-ai/scientific-agent-skills).
- Use explicit domain modeling and red-green-refactor tests, reference-source verification, units/dimensional analysis, numerical benchmarks and critical adversarial review.
- Skills guide workflow; a skill or an AI is never an independent experimental measurement or physics authority.
- Do not introduce a novel scalar-field law or claimed net thrust as an established result.

## Commit and PR procedure

1. Start from the most recent reviewed code baseline. Make a scoped branch and draft PR; preserve the old notebooks until physics interpretation is corrected and validated.
2. Each PR needs: precise claim, source/derivation, boundary conditions, units, assumptions, alternative mechanisms, numeric benchmarks and error analysis.
3. Prefer changes with independent unit/regression tests and source-backed input data. Run relevant tests locally; report them precisely, without implying CI passed before confirming GitHub status.
4. Keep PR in **draft** until an independent adversarial ChatGPT/scientific re-review is completed; implement fixes in branch and request re-review at updated head SHA.
5. When ready for independent review, write a persistent handoff in repo containing: repo, PR number, branch, HEAD SHA, precise changed scope, tests/CI, remaining uncertainty and reviewer acceptance criteria. Announce **READY FOR CHATGPT INDEPENDENT REVIEW** (not merely ready for human review).
6. **Timestamp every readiness handoff.** In both the GitHub PR comment and Antigravity/Hermes's final user-visible status message, include **Issued at (Pacific):** `YYYY-MM-DD HH:MM:SS PDT/PST (UTC offset)` and **Issued at (UTC):** `YYYY-MM-DDTHH:MM:SSZ`. Generate these from the real clock **immediately before posting** (for example, `TZ=America/Los_Angeles date '+%Y-%m-%d %H:%M:%S %Z %z'` and `date -u '+%Y-%m-%dT%H:%M:%SZ'`). Do not recycle the CI completion timestamp or the previous handoff's date. Add the current review round (R3, R4, etc.), source HEAD SHA, and CI run link so completion is unambiguous.
7. **Pickup behavior for every resumed check (manual or scheduled):** refresh PR HEAD, latest GitHub Conversation comments, submitted reviews, and outstanding review threads; read the **newest independent changes-requested review and fix queue**, not just the static handoff. Work on that outstanding queue, run regression tests, push the updated SHA, verify CI/artifacts, and post the timestamped **READY FOR CHATGPT INDEPENDENT RE-REVIEW (R<next>)** handoff. Older READY messages are historical, not evidence that newer findings are resolved. This instruction applies when the agent runs; it does **not** by itself create or verify a scheduler.
8. Do not self-approve or merge based solely on test pass, aesthetics, a patent grant, or speculative interpretation. Merge only with authorization.

## Mandatory README progress synchronization — every project update

**This is a standing definition-of-done rule for Antigravity, Hermes and every implementation agent, including resumed sessions.**

1. **At session start:** read the first-screen project mission, **Project progress**, **How you can support the project**, and current planned visual milestones in README and linked vision. Check the live GitHub main HEAD, draft PRs, newest independent reviews, issue state and CI evidence. Do not rely solely on old handoff text.
2. **On every substantive repository change:** update **README.md in the same branch/PR as the work** to explain in everyday language what changed, which product experience it advances, implementation/verification status, what is planned vs working, what is independently accepted vs under review, blockers and what help is welcome. This applies to new features, UI, code, tests, scientific remediation, design and documentation. Never defer the README update to a later branch or another agent.
3. **Preserve accurate progress:** distinguish implemented, test-passing, independently scientifically accepted, merged, physically measured and speculative. When science-gate totals or stage labels change, update `assets/research-progress.svg` and the README image alt text alongside the narrative. An early educational visual milestone does not add an accepted science gate.
4. **Before committing and at session completion:** inspect README again, verify it against current GitHub/CI and commit its changes with the work. The handoff must state the actual README sections modified, branch and HEAD, relevant CI status, remaining blockers and next visual/scientific action. For a review-only or no-op session, still check and explicitly report **"README progress verified; no status change"**; do not create fake content or needless commits.
5. **Keep public onboarding useful:** the README should immediately explain the project to a curious layperson, link the 3D visual goal and current status, and invite contributions from developers, physicists and experimentalists. Update its "How you can support" and "Project progress" sections when relevant.
6. **CI enforcement for PRs (once merged):** `.github/workflows/readme-progress.yml` runs `scripts/check_readme_progress.py` and its tests on each pull request, including stacked PRs (using the true merge base). Any PR changing files other than `README.md` must also change the text of README's `## Project progress` section in the same PR. A date-only heading change, whitespace-only change or unrelated README edit does not satisfy the gate. README-only edits and empty/no-change sessions do not force fabricated status changes. This guard checks for a change, **not** the truth of a claim: independent review and owner approvals remain mandatory.
7. **Make the check mandatory at merge:** repository owner must configure GitHub Settings → Rules → Rulesets → branch ruleset for `main` with a required status check named `README progress guard / verify`; apply equivalent branch rules for any long-lived stacked base branches if needed. Do not claim merge-blocking enforcement until that repository-side setting is verified. Never skip CI by editing this guard or its workflow in a feature PR; changes to enforcement logic require independent owner review.

These instructions are work rules, **not proof of an automatic Antigravity scheduler or autonomous execution**. Maintain independent scientific review, exact source provenance and owner-only merge authority.
